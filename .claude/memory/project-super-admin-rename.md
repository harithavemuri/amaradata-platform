AmaraData's top-tier role string is `super_admin` everywhere now — `backend/middleware/auth.js`'s guard (renamed `requireSiteAdmin` → `requireSuperAdmin`), `VALID_ROLES` (`admin.js`), `ROLE_PRIORITY` (`auth.js`), `amr_roles`/`amr_users` seed data, frontend nav/badge checks, docs. `database/schema.sql` migration `2026.08.15.003` — `UPDATE amr_roles/amr_users ... WHERE name/role = 'site_admin'` — placed **before** the `amr_roles` seed INSERT in the file (not after, where it was first written), matching the file's existing pattern for the `amr_groups` rename above it: the seed INSERT now targets `'super_admin'` directly, so on an already-provisioned DB an UPDATE running *after* that INSERT hits `amr_roles_name_key`'s unique constraint (reproduced locally, fixed by reordering — see [[feedback-verify-before-responding]]-style lesson: always actually apply a migration to a real DB before calling it done, not just review the SQL).

**Why this specific rename, right now:** triggered by "change Amaradata top role for harithavemuri@gmail.com to super_admin" — user confirmed platform-wide scope, not a single account. Directly unblocks [[project-tenant-modules-sso]]: rohas-group's `SUPER_ROLES = Set(['super_admin','admin'])` doesn't recognize AmaraData's old `'site_admin'` string, so minting an SSO token with the real caller's role would have failed rohas's guard, needing a hardcoded `role: 'admin'` override. After the rename, an AmaraData `super_admin`'s SSO token carries `role: 'super_admin'`, which matches `SUPER_ROLES` exactly — confirmed by the user's own framing: "Amaradata super admin is any tenant's super admin."

**Test-helper convention preserved deliberately:** `tokens.siteAdmin` / `auth('siteAdmin')` (the camelCase property *key* in `src/test/helpers.js` / `testing/unittests/helpers.js`) was **kept as-is** — it's just a JS identifier, not the role value, and renaming it would touch dozens of call sites for no behavioral gain. Only the JWT payload's `role:` field changed, `'site_admin'` → `'super_admin'`. Same reasoning applied to `testing/regression_testsuite/helpers/seed-users.js`'s `SEED_USERS` object, **except** there the key (`SEED_USERS.site_admin`) is spelled identically to the role value, so leaving it stale would read as a real mismatch — that one *was* renamed (`SEED_USERS.super_admin`), with all ~9 spec-file call sites updated to match.

**Bootstrap/smoke accounts also decoupled while doing this** (see [[project-smoketest-account-separation]]): `smoketest.admin` no longer shares the real `harithavemuri@gmail.com` email, and a separate `smoketest.siteadmin` was added as the permanent bootstrap `super_admin` for `scripts/smoke-lifecycle.js`.
