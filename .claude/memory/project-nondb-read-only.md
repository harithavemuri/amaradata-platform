**NonDB mode no longer supports writes.** Every POST/PUT/PATCH/DELETE route across `backend/routes/{admin,auth,contact,email,enhancements,invoices,metrics,subscriptions,tenants}.js` inserts `backend/middleware/block-nondb-write.js`'s `blockNonDbWrite` into its middleware chain (`router.post('/', requireAdmin, blockNonDbWrite, async (req,res)=>{...})`) and has **no** `req.db.mode === 'nondb'` branch anymore — it goes straight to `db.query()`. `blockNonDbWrite` returns `403 { error: 'NonDB mode is read-only — writes are not supported.' }` before the handler runs. GET routes are unchanged (still dual-mode, still read via `req.db.fileDb`).

**Scope, exactly as the user specified:** *all* writes blocked, including the public `contact.js` POST (breaks the marketing contact form under `npm run dev:nondb` — accepted trade-off) and `auth.js`'s `create-user`/`forgot-password`/`reset-password`/Google-OAuth-new-account-creation. **One exception**: the `last_login_at` + `login_audit` bookkeeping write in plain `/api/auth/login`, and the equivalent existing-user branch of `/api/auth/google/exchange`, still write via `req.db.fileDb` even in NonDB mode — "login audit" isn't a data write in the sense being blocked. `google/exchange`'s *new-account* branch (first-time Google sign-in) is still blocked in NonDB mode.

**Why:** User-driven architectural shift — "we will be in read mode when in nondb mode." Directly caused the removal of the old files→DB `sync-to-db`/`sync-status` admin route+button (see [[project-db-write-file-mirror]]) since there's no longer a scenario where NonDB-mode edits need pushing into the DB.

## New feature bundled into the same change: login_audit table

`login_audit` (id, user_id FK, method `password`|`google`, ip_address, logged_in_at) — new table in `database/schema.sql` + `metadata/login_audit.schema.json` + `metadata/manifest.json` + `transactiondata/login_audit.json`. Written on every successful login (both `/login` and `/google/exchange`'s existing-user path), in **both** DB mode (`db.query(INSERT...)`) and NonDB mode (`req.db.fileDb.create(...)`) — this is the "dual write" the user asked for, matching the login-audit exception above.

## Ripple: three test tiers assumed NonDB writes worked — all three needed real fixes, not just deletions

1. **`src/test/*.test.js` dual-mode run** (`vitest.config.nondb.js`) — used to run all 11 route-test files against NonDB expecting writes to succeed. Replaced: `vitest.config.nondb.js` now has `include: ['src/test/nondb-readonly.test.js']` only (a new, narrower file — seeds fixtures directly as files, asserts GET routes still read them, asserts every write route returns 403, asserts the login-audit exception). Full CRUD-workflow coverage of `src/test/*.test.js` stays DB-mode-only (default `vitest.config.js`) — **had to add `**/nondb-readonly.test.js` to that config's `exclude`**, since without it the new file (which assumes `NONDB_MODE=true`) also matched the default config's test glob and failed there.

2. **`testing/unittests/{api,integration}`** — CLAUDE.md always documented this tier as "DB mode only", but `testing/unittests/setup.js` actually set `NONDB_MODE=true` (drift from the documented intent, undetected because NonDB writes used to succeed too). Fixed properly rather than narrowed: `testing/unittests/setup.js` and `testing/global-setup.js` now mirror `src/test/setup.js`/`global-setup.js` exactly (real `_test` Postgres, `TRUNCATE`+seed roles/users via SQL, pool-closing `afterAll`) — **no test file needed changes**, since their assertions expect normal CRUD success, which real DB writes still provide.

3. **`testing/regression_testsuite/` Playwright suite** — defaulted to NonDB mode; its `edit-save-*.spec.js` files create/edit through the real UI. Flipped the default to DB mode (`playwright.config.js`, `global-setup.js`, `global-teardown.js`): `DB_MODE = process.env.REGRESSION_NONDB !== '1'` (was `REGRESSION_DB === '1'`) — **opt in to NonDB now via `REGRESSION_NONDB=1`**, not opt in to DB via `REGRESSION_DB=1`. `login-dashboard.spec.js`'s perf-SLA skip condition flipped to match. `package.json`: `test:regression`/`test:regression:db` both now run DB mode (same thing, kept both names); added `test:regression:nondb`; `test:regression:all` = `test:regression:db && test:regression:nondb`. `scripts/deploy.js` **dropped the "Regression — NonDB mode" phase entirely** (would otherwise fail the whole edit-save suite on every deploy) — NonDB's remaining behavior (reads work, writes blocked) is covered at the API layer by `nondb-readonly.test.js` instead, per this repo's testing-pyramid rule. A narrower NonDB-safe Playwright subset (accessibility, login smoke) could be added back later if wanted; not done here.

4. **`testing/release-tracking/`** (TC-*.spec.js checks) — same NonDB-by-default problem, same fix: `server-entry.js` and `global-setup.js` converted to real DB mode (TRUNCATE + seed tenant/roles via SQL, existing HTTP-based admin-user seeding unchanged since it only needed DB mode to stop being blocked).

## Gotcha that bit twice while doing all this: TRANSACTIONDATA_DIR must be redirected in every DB-mode test entry point

Converting `testing/regression_testsuite/start-server-db.js` and `testing/release-tracking/server-entry.js` to real DB mode means their writes now go through `backend/db.js`'s automatic write-mirror ([[project-db-write-file-mirror]]) — which defaults to the **real, committed `transactiondata/` directory** if `TRANSACTIONDATA_DIR` isn't set. Both files initially lacked the redirect and genuinely overwrote `transactiondata/amr_users.json` and `transactiondata/enhancements.json` during a real test run before this was caught and fixed (restored via `git checkout`). Fixed: `start-server-db.js` → `playwright-testdata/`, `release-tracking/server-entry.js` → `release-tracking/testdata/`. **Any new DB-mode test/dev entry point must set `TRANSACTIONDATA_DIR` to a scratch directory before the app starts, or it will silently corrupt real committed data.** This is now the 4th place this exact mistake was almost made this session (also `src/test/setup.js`, `testing/unittests/setup.js`) — always grep for `TRANSACTIONDATA_DIR` across every test entry point when adding a new one.

## Follow-up bug found in production right after this deployed: write-mirror was silently EROFS-failing on every write

Deploying the write-mirror ([[project-db-write-file-mirror]]) to Lambda immediately started throwing on every DB write in production (caught/swallowed, so it never broke the actual write, but spammed CloudWatch with an ERROR line per write): `EROFS: read-only file system, open '/var/task/transactiondata/amr_users.json'`. Root cause: AWS Lambda's deployment package (`/var/task`, where `TRANSACTIONDATA_DIR` resolves by default) is read-only outside `/tmp`, and `/tmp` is ephemeral/non-persistent/not shared across instances — there was never a way for `fs.writeFileSync` to work there, and the "Sync DB → Files" button never actually worked in production either.

**Fix (user chose the real-persistence option over disabling the feature in prod):** `backend/db.js`'s `mirrorTableToFile()`/`readMirroredTableFile()` branch on `TRANSACTIONDATA_S3_BUCKET` — when set, writes/reads go to S3 (`PutObjectCommand`/`GetObjectCommand`) instead of local disk. Local dev and every test keep the local-disk path unchanged (the env var is never set there).

- New `TransactionDataBucket` S3 resource in `template.yaml` — deliberately **separate from `FrontendBucket`** (different lifecycle/purpose: private DB snapshots vs public CloudFront-served static assets), private, SSE-S3 encrypted.
- `TRANSACTIONDATA_S3_BUCKET` + the S3 IAM policy (`GetObject`/`PutObject`/`ListBucket`, scoped to the new bucket only) are set **only on `ApiFn`**, not in `Globals.Function.Environment.Variables` — `DBInitFn`/`DBMigrateFn` are VPC-attached with no confirmed route to S3, and giving them this env var would turn their existing harmless instant-EROFS-and-continue behavior during migrations into a real network call that could hang instead. Confirmed `ApiFn` itself has no `VpcConfig` (already proven reachable to S3/Secrets Manager via the working email-inbox feature), so it's the one safe place for this.
- `GET /api/admin/sync-from-db/download` (new) — zips whatever's been mirrored (S3 in prod, local disk in dev) via `archiver` and streams it back; this is the *only* way to retrieve the synced snapshot in production, since there's no local file to go look at anymore. `frontend/admin-health.html` gained a matching "⬇ Download Synced Files" link next to the sync button, using the same Bearer-header-blob-fetch pattern `email.html`'s `downloadFile()` already established (plain `<a href>` can't carry the JWT).
- **Test gotcha, same shape as the `pg`/`writePool.query` one**: `vi.mock('@aws-sdk/client-s3', ...)` does not intercept `db.js`'s own nested `require('@aws-sdk/client-s3')` either — confirmed empirically (an unmocked run reached *real* AWS and got a clean `NoSuchBucket` error back, no harm done since that bucket name doesn't exist, but a reminder this class of gotcha applies to every npm-package nested-require in this file, not just `pg`). Fixed by exporting `_s3` from `db.js` so tests can monkey-patch `.send` on the real, never-actually-connected client instance — see `testing/unittests/unit/db-s3-mirror.test.js`.

## Unrelated but real bug found and fixed along the way

`enhancements.issue_id` is Postgres `BIGINT` (OID 20) — `pg` returns it as a **string** by default (same precision-safety default as `NUMERIC`, which `db.js` already had a type parser for). Every caller in this codebase (`enhancements.js`, `jobs/sync-tenant-fixes.js`, tests) treats `issue_id` as a plain number and compares with `===`, so this silently broke `issue_id` lookups whenever code actually ran against real Postgres (never caught before because `testing/release-tracking/` and other issue_id-touching suites only ran against NonDB/FileDbService, which preserves the JS number type). Fixed in `backend/db.js`: `types.setTypeParser(20, v => v === null ? null : parseInt(v, 10))`.
