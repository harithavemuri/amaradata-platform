Built to answer "should the tenants screen show/enable modules per tenant" — rohas-group already has `GET`/`PUT /api/admin/project-modules` (`requireSuperAdminOnly`, checking `SUPER_ROLES=['super_admin','admin']`) and a `project_module_mapping` table, unrelated to AmaraData. User confirmed the approach via `AskUserQuestion`: **SSO token exchange**, reusing AmaraData's existing SSO issuer (`POST /api/auth/sso/issue`) and rohas-group's existing SSO redeemer (`GET /auth/sso`) exactly as they already work for human browser logins — no rohas-group commits (standing rule, [[feedback-amaradata-repo-commits-only]]).

**New files:**
- `backend/services/sso-token.js` — `signSsoToken(secret, {aud,sub,name,role,ttlSeconds})`, extracted from `auth.js`'s `/sso/issue` route so both the HTTP route and the new server-to-server caller share one implementation instead of two copies of the same HMAC-signing logic.
- `backend/services/tenant-sso-client.js` — `callTenantApi(tenant, staff, {method,path,body})`: mints an SSO token for the real calling `staff` (their AmaraData role passes straight through — see [[project-super-admin-rename]] for why that now works without a hardcoded translation), redeems it against `tenant.site_url + '/auth/sso?sso_token=...'` with `fetch(..., {redirect:'manual'})` (rohas's redeemer 302s with the tenant's own session JWT as an `sso_jwt` query param on the `Location` header — must be parsed manually, never followed), then calls the real path with that JWT as `Authorization: Bearer`. All failure modes (no `site_url`, SSO not configured, redemption failed, network error, non-2xx) throw an `Error` tagged `err.tenantUnreachable = true`, which routes translate to a `502`, not a raw `500`.

**Critical design detail, only discovered by reading rohas-group's actual code:** `project_id` in rohas's endpoint is **rohas's own internal "projects" concept** (a real-estate project/property, multiple per tenant site) — completely unrelated to AmaraData's `tenants.id`. AmaraData has no way to know these ids ahead of time, so `GET /api/tenants/:id/modules` calls rohas's GET **unscoped** (no `project_id` query param) to get every project+module row for that tenant site at once (each row already carries `project_name` from rohas's own join), and the `tenants.html` modal groups the flat row list by `project_id` client-side. `PUT` just passes `project_id` through opaquely — AmaraData never needs to understand what it means, only echo back whatever the GET returned.

**New routes** in `backend/routes/tenants.js`: `GET`/`PUT /:id/modules`, `requireSuperAdmin`-gated. `PUT` is idempotent by construction (passthrough to rohas's already-idempotent upsert). `tenants.js`'s `require('../services/tenant-sso-client')` is deliberately **not destructured** (`const tenantSsoClient = require(...)`, then `tenantSsoClient.callTenantApi(...)`) — same reasoning as `writePool`/`readPool` in `db.js`: tests monkey-patch `.callTenantApi` on the shared module object, which only works through a live property read, not a value copied out by destructuring at require time. Verified this exact gotcha by writing the test first assuming destructuring would work — it silently didn't (mock never took effect, real calls happened) — see `src/test/tenant-modules-routes.test.js`.

**Real bug found testing live against the local dev server:** `secrets.getSecret()` throws outright when neither a `secretId` nor a fallback env var is set (documented, intentional — same "not configured" case `/sso/issue` itself already special-cases). `callTenantApi` didn't catch this, so a missing `SSO_SECRET` locally surfaced as an uncaught raw `500` instead of the intended `tenantUnreachable` `502`. Fixed with a try/catch around the `getSecret` call, matching `/sso/issue`'s own pattern; regression test added (`tenant-sso-client.test.js`'s "SSO not configured" case, which deletes `process.env.SSO_SECRET` for one test and restores it after).

Frontend: `frontend/tenants.html` gained an 8th "Modules" column (visible only to `super_admin`, only for tenants with a `site_url`) opening a modal grouped by project, each module a checkbox that `PUT`s on change with inline error display (matches this file's existing `save-err` convention, not a plain `alert()`).
