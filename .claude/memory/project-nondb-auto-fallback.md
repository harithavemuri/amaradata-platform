name: project-nondb-auto-fallback
description: Reads automatically fall back to NonDB (file) mode when the DB is genuinely unreachable, via a request-driven circuit breaker in backend/services/db-health.js — gated strictly to connectivity errors, every occurrence logged, writes unaffected
metadata:
  type: project
---

**What:** `backend/middleware/nondb-mode.js` now has two ways to land a request in NonDB mode: the existing explicit `NONDB_MODE=true` env var (`reason: 'env'`), or automatically when `backend/services/db-health.js`'s circuit breaker reports the DB as down (`reason: 'db_unavailable'`). Both set `req.db.mode = 'nondb'`; routes' existing dual-mode GET branches (`if (req.db.mode === 'nondb') {...}`) work identically either way, with no route code changes needed.

**Why:** User-mandated, given as two explicit constraints up front: "only fall back on connection errors" and "log the errors no matter what." A later message ("log every time you use nondb mode, I may generate an alarm based on number of nondb instances per hour") shaped the logging into a per-request, greppable/countable JSON line rather than a one-time "activated" log — see [[project-db-resilience-strategy]] for the write-side design this sits on top of (unchanged).

**The circuit breaker (`backend/services/db-health.js`):** `markDown(err)` / `markUp()` / `shouldTryDb()`. Deliberately **not** a background `setInterval` prober — Lambda freezes the process between invocations, so a timer wouldn't reliably fire. Instead it's a lazy, request-driven "half-open" breaker: once `RECHECK_COOLDOWN_MS` (default 15s, override via `DB_HEALTH_RECHECK_MS`) has elapsed since the last known failure, the next incoming request is simply routed to DB mode as a trial — if it fails, `markDown()` fires again and the cooldown window restarts (this reset-on-every-failure behavior, not just first failure, is what makes the breaker self-correcting without a timer).

**Gated strictly to connection errors:** `backend/db.js`'s `query()` is the only caller of `markDown()`/`markUp()`, and only ever passes `isConnectivityError(err)`-true cases (`backend/services/db-retry.js`'s existing classifier — network-level codes, "connection terminated", etc.). A query error (bad SQL, unique-violation, anything else) never touches this module and is untouched by any of this — it still surfaces through the pre-existing generic-500 path.

**Logging "no matter what":** every `markDown()` call logs, including repeats while already down (e.g. a failed half-open trial) — not just the healthy→down transition. For reads, `withConnectRetry`'s `onRetry` callback fires before each retry's backoff sleep, and the final exhausted-retries throw is caught once more outside the retry loop, so all 3 attempts of a fully-exhausted read get logged, not just the last one. `nondb-mode.js` separately logs every single NonDB-mode *request* (`event: 'nondb_request'`, tagged with `reason`) — this is the log the user's per-hour alarm is meant to count, distinct from the connectivity-error log itself.

**Writes are completely unaffected — this is a reads-only fallback:** `backend/middleware/block-nondb-write.js` still unconditionally blocks every write when `req.db.mode === 'nondb'`, regardless of `reason` — a write must never reach file storage either way (explicit user instruction: "when in nondb mode don't allow writes to files"). The only thing `reason` changes is the response shape: `reason === 'db_unavailable'` gets the exact same `503 { error: 'Service temporarily unavailable — please retry shortly.' }` every other DB-outage write failure in this codebase already returns (`services/http-errors.js`'s `sendError`), not the structural `403 { error: 'NonDB mode is read-only...' }`, which would misleadingly imply a permanent policy rather than a temporary outage. Writes never get routed to NonDB mode's fileDb path at all — they always attempt the real DB (bypassing the breaker's read-side throttling entirely), so an outage is detected on the very next write attempt regardless of the breaker's current state.

**Gotcha hit while testing this:** chaining multiple `mockRejectedValueOnce()` calls up front in a fake-timers test constructs all the `Promise.reject()` instances immediately, before a multi-attempt retry loop's backoff has even started — later ones sit unobserved long enough to trip Node's unhandled-rejection detector (`PromiseRejectionHandledWarning`, which still fails the Vitest run despite every individual test passing — caught via checking the actual exit code, not just scanning output, per [[feedback-verify-exit-codes]]). Fixed by using `mockImplementation(() => Promise.reject(err))` instead, which creates the rejection fresh at call time. See `testing/unittests/unit/db-query-resilience.test.js`'s "marks db-health down once per exhausted-retries failure" test.

Tests: `testing/unittests/unit/db-health.test.js` (breaker state machine in isolation — cooldown, reset-on-repeat-failure, recovery logging), `db-query-resilience.test.js` (db.js calls markDown/markUp at the right points, reads and writes), `nondb-mode-middleware.test.js` (mode/reason selection + per-request logging), `block-nondb-write.test.js` (unconditional block, reason-aware response shape).
